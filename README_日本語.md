# E-GEO 日本語転移実験ガイド

この文書は、英語版E-GEOの実験設計を土台として、日本語のTOEIC教材検索における商品説明リライトの効果を検証するための作業ガイドです。

コマンドは、原則としてリポジトリ直下の `E-GEO/` で実行します。日本語実験は作業ブランチ `ja-toeic-prototype` で進めます。

---

## 1. 研究目的

原版E-GEOは、対象商品の説明文だけを書き換え、同じ検索クエリ・同じ候補商品10件の中で対象商品の順位がどのように変化するかを測る研究です。

本研究では、楽天ブックスから収集した日本語のTOEIC教材データを用いて、次の問いを検証します。

### 主研究

> 英語で得られたE-GEOの汎用リライト戦略は、日本語の商品検索でも順位改善に有効か。

### 追加検証

> 同じ購入意図でも、短い検索キーワードと自然な長文の購入相談では、商品説明リライトの効果が異なるか。

本研究で変更するのは、候補商品10件のうち対象商品1件の説明文だけです。検索クエリ、候補商品、商品名、価格などは条件間で固定します。

## 2. 原版E-GEOとの対応

| 項目 | 原版E-GEO | 本研究 |
|---|---|---|
| 言語 | 英語 | 日本語 |
| 商品領域 | 複数カテゴリ | TOEIC教材に限定 |
| クエリ | 長文の購入相談 | 短文クエリ＋対応する長文クエリ |
| 商品データ | Amazon英語商品 | 楽天ブックスのTOEIC教材 |
| 候補商品数 | 1クエリにつき10商品 | 同じく10商品 |
| 書き換え対象 | 候補10商品のうち1商品 | 同じく1商品 |
| Rewriterへの入力 | 汎用リライト指示＋商品説明 | 同じ。評価クエリは原則渡さない |
| Re-rankerへの入力 | クエリ＋候補商品10件 | 同じ |
| 主評価指標 | 書き換え前後の平均順位改善 | 同じ |
| 追加分析 | なし | 短文・長文、モデル別の比較 |
| 実験規模 | 大規模 | API予算100ドル以内の小規模実験 |

重要なのは、商品説明を書き換える **Rewriter** と、候補商品を順位付けする **Re-ranker** を分けることです。

```text
汎用リライトプロンプト＋対象商品説明
        ↓
Rewriterが対象商品の説明だけを書き換える
        ↓
検索クエリ＋候補商品10件
        ↓
Re-rankerが1位から10位まで順位付け
        ↓
対象商品の書き換え前後の順位差を計算
```

## 4. データクレンジング方針

元データには、電子書籍、説明文欠損、表記揺れ、商品名への著者名混入などが含まれる可能性があります。元Excelは直接編集せず、Pythonで加工済みデータを作成します。

主な処理は次のとおりです。

1. ISBNと価格を数値として扱える形式へ整形する
2. タイトル・著者・出版社・発売日・形式を可能な範囲で分離する
3. HTMLタグ、見出し、余分な改行・空白を除去する
4. `TOEIC?L&R`などの文字化けを修正する
5. 電子書籍、TOEIC教材ではない商品、説明文欠損を除外する
6. 紙版・電子版、旧版・改訂版などの実質重複を確認する
7. 除外理由を列として記録する
8. 実験に使用する約200商品を固定する

商品説明は、短すぎて内容を判断できないものを除外します。最低文字数は分布を確認してから固定し、処理後に変更しません。

## 5. 実験データ設計

### 商品数

クレンジング後の商品から、実験用に約200商品を使用します。

### 購入意図

合計80件の購入意図を作成します。各購入意図には、意味を対応させた短文クエリと長文クエリを1件ずつ用意します。

| 分割 | 購入意図数 | クエリ表現数 |
|---|---:|---:|
| Train | 40 | 80 |
| Validation | 10 | 20 |
| Test | 30 | 60 |
| 合計 | 80 | 160 |

### 1購入意図の構成

```text
短文クエリ1件
長文クエリ1件
候補商品10件
正解対象商品1件
対象商品を選んだ根拠
```

短文と長文では、候補商品10件と対象商品1件を完全に同じにします。

例：

```text
短文：
TOEIC 600点 初心者 総合対策

長文：
現在のスコアが450点前後で、まず600点を目指しています。
単語だけではなく、リスニングとリーディングを一冊で基礎から学べる教材を探しています。
```

### 候補商品10件の作り方

対象商品1件は、その購入意図を最も満たす商品として、商品説明と教材の特徴を確認して固定します。残り9件は、同じ購入意図に対して比較対象になり得るTOEIC教材から選びます。

候補商品は、難易度・目標点・学習分野・教材形式が極端に離れすぎないようにします。簡単に正解できる候補集合ではなく、実際の比較検討に近い候補集合を作ります。

### データ漏洩の防止

- 分割は購入意図単位で行う
- Testの購入意図はプロンプト作成・選択に使用しない
- Testの対象商品はTrain・Validationの対象商品に使用しない
- Testの対象商品は、可能な限りTrain・Validationの候補集合にも含めない
- 候補商品は複数の購入意図で再利用してよいが、対象商品と分割情報を記録する
- 分割後は乱数シードとデータファイルを固定する

200商品だけで80組×10件を構成するため、候補商品の再利用は許可します。ただし、対象商品の分割漏洩を優先して防ぎます。

## 6. 比較条件

次の4条件を比較します。

| 条件 | 内容 |
|---|---|
| Original | 商品説明を書き換えない |
| EN-Zero | 原版E-GEOの英語最適化プロンプトを日本語商品へゼロショット適用 |
| JA-Zero | 英語プロンプトを自然な日本語へ翻訳してゼロショット適用 |
| JA-Adapted | Train・Validationを使って日本語向けに調整したプロンプトを適用 |

すべての条件で、商品名、候補商品、候補順、検索クエリ、Re-rankerの設定を固定します。

Rewriterには、原則として評価対象の検索クエリを渡しません。商品説明そのものを検索されやすく、具体的で、事実に忠実な文章へ改善できるかを検証します。

商品説明に存在しない機能、対象スコア、特典、実績などを追加することは禁止します。書き換え後は、元説明との整合性を確認します。

## 7. モデル設定

最終Testでは、3種類のRe-rankerモデルを使用する予定です。具体的なモデル名とバージョンは少数件のパイロット後に固定します。

比較の公平性を保つため、次を守ります。

- 同一モデル内では全条件で同じtemperature・最大出力・指示文を使用する
- 候補商品10件の提示順を条件間で固定する
- 可能なら候補順による位置バイアスを確認する
- モデル名、提供元、実行日、設定値を結果ファイルへ保存する
- JSONなどの構造化出力を使い、順位の欠損・重複を検査する
- 失敗した呼び出しと再実行回数を記録する

最終Testの順位付け回数の目安は次のとおりです。

```text
30購入意図
× 2クエリ長
× 4条件
× 3モデル
= 720回
```

Test対象30商品のリライト回数は、3種類のリライト条件で約90回です。Train・Validationでの最適化分は別に管理します。

## 8. 評価指標

主指標は、原版E-GEOと同じ平均順位改善量です。

```text
順位改善量 ＝ 書き換え前の順位 − 書き換え後の順位
```

例：

```text
書き換え前：7位
書き換え後：3位
順位改善量：+4
```

合わせて次を記録します。

- 平均順位改善量
- 順位改善量の中央値
- 順位が上昇・不変・低下した割合
- Top 1、Top 3、Top 5到達率
- Re-rankerモデル別の結果
- 短文クエリと長文クエリの差
- リライト条件間の差
- 入力・出力トークン数
- 推定API費用
- 失敗率と再実行回数

同じ購入意図・同じ対象商品を条件間で比較するため、対応のある分析を基本とします。統計手法はデータ分布と件数を確認してから固定します。

## 9. API料金の管理

研究全体のAPI予算上限は100ドルです。

- 最初に5件程度で動作確認する
- 次に10〜20件で費用と出力品質を確認する
- 各呼び出しの入力・出力トークン数を保存する
- モデル別・処理別の推定費用をCSVへ記録する
- 推定累計費用が60ドルで警告する
- 推定累計費用が80ドルに達したら新規API処理を停止する
- 残り20ドルは失敗時の再実行と予備に残す
- 同じ商品説明のリライト結果はキャッシュして再利用する

`.env`に保存したAPIキーはGitHubへpushしません。

```dotenv
OPENAI_API_KEY=<自分のAPIキー>
OPENROUTER_API_KEY=<自分のAPIキー>
```

APIを使うスクリプトには、少数件モード、実行前の費用見積もり、途中再開、重複実行防止を設けます。
